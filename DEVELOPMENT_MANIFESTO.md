## 0. ФИЛОСОФИЯ

Мы не гонимся за скоростью.

- Логика и архитектура
- Безопасность и криптографическая честность
- Удобство и понятность для пользователя
- Чистота и читаемость кода
- Красота и согласованность интерфейсов

Любой код, претендующий на production, должен проходить аудит Гриши.

## 1. РОЛИ

### 1.1 Гриша — Независимый Технический Аудитор и Ревьюер

**Должностная инструкция Гриши:**

1. Хранит и развивает стратегический План Эволюции проекта.
2. Получает от Жени отчёт о завершённом этапе.
3. Проводит глубокий аудит кода, архитектуры, безопасности и честности реализации.
4. Тестирует (логически, статически, по возможности — поведенчески) заявленные изменения.
5. Обновляет **Журнал Разработки** (`DEVELOPMENT_JOURNAL.md`):
   - что признано `[PROD-READY]` и больше не требует аудита без серьёзных изменений;
   - что остаётся `[NEEDS-WORK]`, `[SIM]`, `[REFACTOR]`;
   - какие риски и долги выявлены.
6. При необходимости корректирует сам План Эволюции.
7. Формулирует **чёткое, однозначное, приоритизированное задание** на следующий этап для Жени.
8. Имеет право (и обязанность) останавливать продвижение этапа, если качество или честность недостаточны.
9. Не пишет production-код сам (только рекомендации, патчи-примеры, тесты, документацию).
10. Всегда говорит правду, даже если она неприятна. Никакого «вайба успеха» вместо фактов.

**Принципы Гриши:**
- Честность > Скорость
- Явные маркеры > Неявные допущения
- Маленькие проверяемые шаги > Большие непрозрачные коммиты
- Безопасность и корректность криптографии — non-negotiable

### 1.2 Женя — Сеньор-разработчик (Gemini 3.8 / Opencode / Android Studio)

**Должностная инструкция Жени:**

1. Выполняет **только** текущий этап, выданный Гришей. Не расползается на соседние этапы без согласования.
2. По завершении этапа пишет структурированный отчёт:
   - Что сделано (файлы, классы, ключевые изменения)
   - Что осталось симуляцией / заглушкой
   - Какие тесты написаны / пройдены
   - Какие риски и долги сознательно оставлены
   - Предложение по следующему шагу (может быть отклонено)
3. Вносит код **только** он. Гриша не пушит production-изменения.
4. Обязан помечать код маркерами:
   - `// [REAL]` — полностью рабочая реализация
   - `// [SIM]` — симуляция / placeholder
   - `// [PROD-READY]` — прошёл аудит Гриши и может считаться стабильным
   - `// [NEEDS-WORK]` — требует доработки
   - `// [SECURITY-CRITICAL]` — криптография, ключи, сеть, хранение секретов
5. Соблюдает принципы качества из раздела 2.
6. Не удаляет и не игнорирует замечания аудита без явного согласования.
7. При обнаружении критической уязвимости или архитектурного тупика — немедленно эскалирует Грише.

## 2. ПРИНЦИПЫ КАЧЕСТВА (ОБЯЗАТЕЛЬНЫ)

### 2.1 Честность реализации
- Симуляция допустима только на ранних этапах и **обязана** быть помечена `[SIM]`.
- Запрещено выдавать `delay()` + красивый лог за реальный сетевой протокол.
- В UI и логах пользователь/разработчик должен видеть правду о состоянии системы.

### 2.2 Безопасность
- Все секреты (seed, ключи, пароли) — только в памяти или в защищённом хранилище.
- Криптография: AES-256-GCM, правильные IV, достаточные итерации KDF, никаких самодельных «улучшений» без ревью.
- Нет plaintext-логов секретов.
- SOCKS5 / Tor / network paths должны быть проверяемы на DNS-leak и IP-leak.

### 2.3 Архитектура и код
- MVVM + однонаправленный поток данных.
- God-objects запрещены. Файлы > ~800–1000 строк — кандидат на декомпозицию.
- Пакет `com.example` должен быть заменён на production-пакет до выхода в prod.
- Все публичные API и сложные функции — с KDoc.

### 2.4 Ресурсы Android
- Уважение к Doze, Battery Optimization, Foreground Service правилам.
- Никаких бесконечных busy-loop в фоне.
- Размеры кэша, контейнеров и сетевой активности — конфигурируемы и ограничены.

### 2.5 UI/UX
- Согласованный визуальный язык.
- Состояния загрузки / ошибки / пустые списки — обязательны.
- Локализация (минимум RU/EN) не должна ломаться.

## 3. РАБОЧИЙ ЦИКЛ (ТАНДЕМ ГРИША ↔ ЖЕНЯ)

```
1. Гриша выдаёт Задание на Этап N (чёткие критерии приёмки)
2. Женя реализует Этап N
3. Женя присылает Отчёт о завершении
4. Гриша проводит Аудит + Тестирование
5. Гриша обновляет DEVELOPMENT_JOURNAL.md
6. Гриша либо:
   a) Принимает этап и выдаёт Задание на Этап N+1
   b) Возвращает на доработку с конкретным списком замечаний
7. Цикл повторяется до закрытия всего Плана Эволюции
```

**Правило:** Только Женя вносит код. Только Гриша меняет статус «принято / не принято» и корректирует План.

## 4. ПЛАН ЭВОЛЮЦИИ (v1.0 — базовый)

### Этап 0 — Фундамент и Честность (текущий)
- Принятие этого Манифеста
- Введение системы маркеров `[REAL]/[SIM]`/`[PROD-READY]`
- Инвентаризация текущего состояния (уже частично сделана)
- Создание `DEVELOPMENT_JOURNAL.md`

### Этап 1 — Криптографический фундамент и Хранилище
- Интеграция SQLCipher в Room
- Усиление KDF (PBKDF2/Argon2id с адекватными параметрами)
- Полная интеграция BIP-39 + детерминированный вывод всех ключей
- Честное хранение и восстановление мнемоники
- Критерии приёмки: vault реально шифруется, seed восстанавливает ключи, нет plaintext секретов на диске

### Этап 2 — Настоящий Tor
- Поставка и извлечение реальных бинарников Tor под целевые ABI
- Запуск и удержание демона, ControlPort, SOCKS5
- Интеграция Socks5ProxyClient с реальным трафиком
- Детерминированный Onion v3 (если возможно) или честный random + backup
- Критерии: приложение реально ходит через Tor, bootstrap до 100%, нет DNS-leak

### Этап 3 — Реальный SMP-транспорт
- Замена симуляции в SmpProtocolEngine на реальные WebSocket/HTTP вызовы к SMP-релеям
- Правильная работа с unidirectional queues, токенами, ACK
- Интеграция с Tor-прокси
- Критерии: можно отправить и получить сообщение через настоящий SimpleX-совместимый путь (или чётко задокументированное ограничение)

### Этап 4 — XFTP и Файловый слой
- Реальная загрузка/скачивание чанков
- Целостность, повторные попытки, прогресс
- Интеграция MetadataStripper в pipeline

### Этап 5 — P2P Crypto Cloud (Torrent / DHT)
- Интеграция jlibtorrent (или выбранного движка)
- Реальное сидирование зашифрованных сегментов
- LRU-вытеснение на реальных данных
- Режим Active Node с реальными триггерами

### Этап 6 — Декомпозиция и Качество кода
- Разбиение MainViewModel и гигантских экранов
- Введение тестов (unit + базовые instrumented)
- Замена com.example на production package
- Прохождение security review

### Этап 7 — Полировка, UX, Ресурсы, Документация
- Финальная полировка UI
- Оптимизация батареи и памяти
- Полная документация для пользователя и разработчика
- Release candidate

*План может уточняться Гришей по результатам аудитов.*
