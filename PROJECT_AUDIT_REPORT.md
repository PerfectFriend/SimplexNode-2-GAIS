# Отчёт по результатам ревизии проекта: Децентрализованное крипто-облако ParanoidX Node (SimpleX + SOCKS5 + Tor)

Этот отчёт содержит детальный анализ текущего состояния кодовой базы, разделение функционала на реально работающий и симулированный, описание непреодолимых платформенных ограничений Android, а также обновленный стратегический план эволюции системы с учетом требований по анонимности, энергосбережению и автономности.

---

## 1. Введение и Архитектурная концепция

Проект представляет собой сверхзащищенный клиент-серверный узел для однонаправленного P2P-обмена сообщениями (по протоколу **SimpleX**) и распределенного хранения зашифрованных резервных копий (**Decentralized Crypto Cloud**), переименованный в **ParanoidX Node**.

### Ключевые столпы безопасности и приватности системы:
1. **Анонимность метаданных**: Отсутствие глобальных идентификаторов пользователей. Связь строится на изолированных однонаправленных очередях доставки (SimpleX Tubes).
2. **Криптографическая стойкость на базе BIP-39**:
   * Генерация аккаунта и всех ключей доступа производится из детерминированной **12- или 24-словной мнемонической фразы BIP-39**.
   * Из единого мастер-соли (BIP-39 Entropy Seed) через алгоритм HKDF детерминированно выводятся:
     1. Мастер-ключ шифрования сейфа (AES-256-GCM).
     2. Приватный ключ Tor v3 Hidden Service (Ed25519) — это гарантирует сохранение одного и того же адреса `.onion` при восстановлении на любом устройстве.
     3. Первичные пары ключей Double Ratchet для мессенджера.
     4. Детерминированный поисковый хэш DHT (DHT Search Info-Hash), позволяющий анонимно находить и восстанавливать зашифрованные бэкапы прямо из P2P-облака без участия централизованных серверов.
3. **Область туннелирования (SOCKS5)**: Полная инкапсуляция трафика через локальные SOCKS5-прокси (Tor / Tailscale) для предотвращения утечек реального IP-адреса и обхода локальных блокировок.
4. **Физический криптоконтейнер вместо RAM**:
   * Выделение зарезервированного дискового пространства на Flash/UFS-накопителе устройства (размер настраивается в параметрах UI: 16, 32, 64 ГБ).
   * Использование разреженного зашифрованного файла-контейнера (`vault_container.bin`), внутри которого посекторно распределяются и шифруются части торрент-блоков. RAM используется исключительно как ультракороткий буфер обмена (не более нескольких мегабайт).
5. **Умная фоновая синхронизация (Режим Активной Ноды)**:
   * Автоматическая фоновая репликация работает незаметно и деликатно.
   * Процесс активируется только при совпадении критериев: телефон подключен к зарядному устройству (режим док-станции), обнаружена быстрая Wi-Fi сеть с низкой задержкой (ping < 50мс), и система простаивает (экран выключен, CPU свободен).
   * Включение специального режима **"Активная Нода"** превращает устройство в полноценный высокоскоростной P2P-релей на время сна пользователя.
6. **Кэширование по алгоритму LRU с защитой папок**:
   * При достижении лимита выделенного дискового пространства, нода автоматически производит ротацию кэша.
   * Она находит временные или транзитные торрент-куски, к которым обращались наиболее давно (алгоритм *Least Recently Used - LRU*), и безвозвратно удаляет их, освобождая место под новые данные.
   * Защищенные папки («Сейф» и файлы, помеченные флагом «Закреплено/Pinned») полностью исключены из этого алгоритма ротации и никогда не стираются автоматически.

## 2. Что реализовано на 100% (Полный рабочий функционал)

Данные модули полностью интегрированы в UI/UX Jetpack Compose, связаны с реактивными потоками данных (`StateFlow`) в `MainViewModel` и готовы к работе на уровне логики приложения:

*   *## 3. Что симулировано (Ожидает дальнейшей низкоуровневой реализации)

Для демонстрации полной концепции без перегрузки мобильного устройства на этапе прототипирования следующие тяжелые сетевые механизмы работают в режиме симуляции:

1.  **Бинарный сокет SOCKS5 (Tor Daemon)**:
    *   *Как работает сейчас*: При отправке сообщений в SimpleX ViewModel проверяет состояние прокси, рассчитывает задержку, симулирует TCP-подключение к локальному порту 9050, проводит логический обмен кадрами аутентификации и DNS-запроса, после чего проводит успешную транзакцию. Фоновая служба `TorDaemonService` имитирует запуск, логируя процесс развертывания SOCKS-прокси.
    *   *Что нужно внедрить*: Настоящее перенаправление сокетов Java (`java.net.Socket` с передачей `java.net.Proxy(Proxy.Type.SOCKS, ...)`), подключенное к фоновому демону Tor (например, через интеграцию библиотеки Orbot или NetCipher/OnionKit).
2.  **Движок торрент-сегментации (P2P Torrent Engine) и LRU-вытеснение**:
    *   *Как работает сейчас*: Фоновый поток (`Kotlin Coroutines`) в `MainViewModel` имитирует скачивание распределенных частей (pieces), случайным образом завершая загрузку секторов, имитируя флуктуацию пиров в рое (Swarm), изменение скорости и задержку в зависимости от переключателя Wi-Fi/Cellular.
    *   *Что нужно внедрить*: Настоящий торрент-сессионный менеджер на базе `jlibtorrent`. При заполнении кэша контейнера до установленной отметки (например, 90% от лимита в 32 ГБ), фоновый воркер запускает процедуру LRU-вытеснения: сканирует базу метаданных торрент-кусков, находит блоки временных транзитных раздач с самой старой временной меткой последнего обращения (`last_access_timestamp`), удаляет их физические файлы с накопителя и перезаписывает свободные секторы нулями. При этом папки с флагом `is_pinned` (закрепленные) полностью игнорируются при сканировании.
3.  **Виртуальное монтирование Cryptocontainer**:
    *   *Как работает сейчас*: Приложение создает зашифрованную резервную копию в закрытой директории приложения (Sandbox) и симулирует резервирование виртуального пространства на диске.
    *   *Что нужно внедрить*: Использование виртуального зашифрованного контейнера на физическом накопителе устройства (Flash/UFS) с файловой системой FAT32/EXT4. Доступ к нему осуществляется через DocumentsProvider (Storage Access Framework) Android, чтобы пользователь мог взаимодействовать с криптоконтейнером как с внешним USB-накопителем прямо из проводника.
4.  **BIP-39 Мнемонический генератор**:
    *   *Как работает сейчас*: Пользователь задает пароль для сейфа, и приложение шифрует данные с использованием полученного AES ключа.
    *   *Что нужно внедрить*: Генерация 12/24 слов из BIP-39 словаря. Слова конвертируются в 512-битное семя (seed). С использованием HKDF-Sha512 порождается иерархия ключей (HD-Wallet структура): ветка `/0` для ключа шифрования Vault, ветка `/1` для секретного ключа скрытого Tor-сервиса (Onion Ed25519) для переносимости адреса, ветка `/2` для SimpleX чата и ветка `/3` для генерации уникального CID/InfoHash торрента бэкапа.

## 4. Что НЕ МОЖЕТ быть реализовано (Платформенные ограничения Android)

В силу специфики архитектуры ОС Android и ограничений безопасности (Sandboxing), некоторые десктопные концепции не могут быть перенесены напрямую:

*   **Выделение ОЗУ (RAM) под криптоконтейнер**:
    *   *Причина*: Смартфоны имеют ограниченный объем физической оперативной памяти, а среда выполнения Android жестко лимитирует размер кучи (heap size) для одного приложения (редко более 512 МБ). Попытка зарезервировать 16-64 ГБ в RAM мгновенно вызовет аварийное завершение `OutOfMemoryError`.
    *   *Решение*: Использование физического выделенного пространства на постоянном накопителе (Flash/UFS) в виде зашифрованного файла-контейнера (`vault_container.bin`). RAM задействуется только как временный ультракороткий буфер для чтения/записи отдельных блоков размером 16 КБ.
*   **Низкоуровневое монтирование дисков (LUKS / TrueCrypt / dm-crypt)**:
    *   *Причина*: Монтирование полноценных зашифрованных разделов на уровне ядра Linux в Android требует прав суперпользователя (`root`). Без root-прав приложение не имеет доступа к `/dev/block` и командам `mount`.
    *   *Решение*: Использование полностью пользовательских (User-space) реализаций файловых систем (FAT32 внутри файла), работающих внутри песочницы приложения, и экспорт файлов через Android Storage Access Framework.
*   **Бесконечная фоновая работа Torrent-раздачи без уведомлений**:
    *   *Причина*: Системы энергосбережения (Doze Mode, App Standby Bucket) в Android 12+ нещадно убивают любые фоновые сокеты и потоки через несколько минут после сворачивания приложения.
    *   *Решение*: Обязательный запуск неубиваемого фонового сервиса (**Foreground Service**) с отображением постоянного уведомления в статус-баре устройства и получением системного разрешения `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.

## 5. Полный стратегический план предстоящей эволюции

Для поэтапного перевода симулированных функций в боевой режим предлагается следующий роадмап:

### Этап 1: Стабилизация криптографии, BIP-39 и БД (Ближайшие задачи)
1.  **Интеграция SQLCipher**: Перевести локальную базу данных Room с открытого SQLite на зашифрованный **SQLCipher** для автоматического посекторного шифрования базы данных сейфа "на лету" с использованием ключа, вводимого пользователем при разблокировке.
2.  **BIP-39 Генерация**: Интегрировать библиотеку `bitcoinj-core` (или легковесную `bip39` для Kotlin) для создания мнемоник, детерминированного вывода ключей шифрования и восстановления профиля ноды из бэкапа.

### Этап 2: Переход от симуляции сокетов к реальному Tor SOCKS5
1.  **Внедрение Tor-Android-Binary (Guardian Project)**:
    *   Подключить библиотеку `com.github.guardianproject:tor-android-binary` в `build.gradle.kts`.
    *   Реализовать извлечение бинарного файла демона Tor под целевую архитектуру процессора и запуск процесса с конфигурацией скрытого сервиса (Hidden Service v3), детерминированного из BIP-39 сида.
2.  **Локальный прокси-клиент**: Обучить приложение выполнять все SimpleX HTTP-запросы и сокет-соединения строго через прокси `127.0.0.1:9050` (SOCKS5).

### Этап 3: Создание реального P2P-облака хранения с LRU-вытеснением
1.  **Интеграция Frostwire-JLibtorrent**:
    *   Добавить облегченную обертку над libtorrent для Android.
    *   Написать менеджер раздач, который будет упаковывать зашифрованный сейф во временный `.torrent`-файл, генерировать magnet-ссылку и анонсировать ее в DHT.
2.  **Разработка алгоритма LRU-кэша**:
    *   Разработать фоновый планировщик, который при заполнении дисковой квоты контейнера выполняет запрос: `SELECT * FROM shared_files WHERE is_pinned = 0 ORDER BY last_access_timestamp ASC` и удаляет самые старые неиспользуемые куски до освобождения нужного объема памяти.

### Этап 4: Разработка интеллектуального фонового демона синхронизации
1.  **Умный триггер мониторинга ресурсов**:
    *   Зарегистрировать приемник широковещательных сообщений (`BroadcastReceiver`) для отслеживания состояния зарядного устройства (`Intent.ACTION_POWER_CONNECTED`) и активности экрана (`Intent.ACTION_SCREEN_OFF`).
    *   Использовать `ConnectivityManager` для оценки пропускной способности Wi-Fi и пинга до релейного узла (ping до шлюза < 50мс).
2.  **Режим "Активная Нода"**:
    *   Реализовать специальный экран режима ожидания (Dock Mode UI). Когда телефон ставится на зарядку ночью на Wi-Fi, включается полноэкранный терминал, визуализирующий активную сетевую пересылку данных, сидирование торрент-блоков и синхронизацию DHT-таблиц.
    *   Интегрировать с `Android WorkManager` для запуска тяжелых задач резервного копирования только в моменты глубокого сна устройства.

## Заключение

Текущая версия проекта представляет собой **высокотехнологичный прототип и идеальную архитектурную модель** защищенного P2P-клиента **ParanoidX Node**. Все критически важные интерфейсы, защитные механизмы, реактивные терминалы логов и логика переключения сетевых сред полностью подготовлены для бесшовной интеграции низкоуровневых библиотек Tor и BitTorrent на последующих этапах разработки. С добавлением BIP-39 детерминированных ключей и адаптивного алгоритма LRU-кэширования проект закладывает идеальный фундамент для бескомпромиссной конфиденциальности на мобильных устройствах.
