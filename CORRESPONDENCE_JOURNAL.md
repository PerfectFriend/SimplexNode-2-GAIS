### Правила ведения журнала (обязательны для обеих сторон)

1. Каждое новое сообщение добавляется **строго в конец** файла.
2. Сообщения не удаляются, не переписываются и не «исправляются задним числом».
3. Каждое сообщение начинается с заголовка следующего формата:

```
---
**[YYYY-MM-DD HH:MM TZ]** | От: [Имя] | Кому: [Имя] | Тип: [СООБЩЕНИЕ / ОТЧЁТ / АУДИТ / ЗАДАНИЕ / ЗАМЕЧАНИЕ / ПРИНЯТИЕ / ВОЗВРАТ]
**Тема:** краткая тема
```

4. После заголовка идёт тело сообщения.
5. В конце сообщения рекомендуется ставить разделитель `---` или просто оставлять пустую строку перед следующим заголовком.
6. Допускаются теги внутри текста: `[REAL]`, `[SIM]`, `[PROD-READY]`, `[NEEDS-WORK]`, `[SECURITY-CRITICAL]`, `[ЭТАП-N]` и т.д.

### Отчёт по выполнению Этапа 5 (P2P Crypto Cloud)

1. **Физический дисковый криптоконтейнер (`P2pBlockStorage.kt`)**:
   - Реальное поблочное хранение в изолированной песочнице приложения (`files/p2p_container/blk_{hash}.bin`).
   - Каждый блок индивидуально зашифрован AES-256-GCM мастер-ключом хранилища.
   - Валидация SHA-256 хеша: при записи блок сверяется с объявленным хешем; при чтении после расшифровки вычисляется и сверяется SHA-256. В случае повреждения чтение прерывается.
   - Реальный подсчёт физического размера хранилища на диске (`getContainerSizeBytes()`).
   - Реальное LRU-вытеснение устаревших блоков (`evictLru(limitBytes)`): при превышении установленного лимита (GB) удаляются самые старые блоки по времени обращения (`lastAccessTime`).

2. **Сетевой движок P2P и micro-peer сервер (`P2pCloudEngine.kt`)**:
   - Встроенный локальный HTTP/P2P micro-server (порт 6881 или динамический) для приёма и раздачи блоков роем:
     - `GET /p2p/ping`: отдача статуса ноды, nodeId и количества доступных блоков;
     - `GET /p2p/blocks/{hash}`: отдача зашифрованного блока из криптоконтейнера с учётом переданных байт в исходящую скорость (upload throughput);
     - `POST /p2p/blocks/{hash}`: приём блока от пира, проверка хеша, сохранение на диск и учёт входящих байт (download throughput).
   - Сетевой клиент `OkHttpClient` с опциональной маршрутизацией через Tor SOCKS5 (`127.0.0.1:9050`) и защитой от утечек DNS (`InetSocketAddress.createUnresolved`).
   - **Честное измерение задержки**: метод `measureRealLatency(host, port)` выполняет реальный socket connect probe и возвращает фактическое время кругового обхода в миллисекундах. Никаких `(20..150).random()`.
   - **Честные скорости**: расчёт пропускной способности ведётся строго по фактически переданным байтам за временное окно. В простое — честные `0 KB/s`.

3. **Служба раздачи и режим Active Node (`TorrentSeederService.kt`)**:
   - Аппаратная телеметрия: зарядка (`ACTION_POWER`), активность экрана (`ACTION_SCREEN_ON/OFF`), сеть (`ConnectivityManager.NetworkCallback`).
   - Честные статусы узла:
     - `NO_NETWORK` — сеть разорвана или включён режим «Только Wi-Fi» на мобильном интернете;
     - `ACTIVE_RELAY` — статус Active Node активируется строго при выполнении всех условий: зарядка подключена, Wi-Fi активен, экран выключен и реальный пинг < 80ms;
     - `SEEDING` / `DOWNLOADING` / `IDLE` — по фактической активности.
   - Периодическая проверка и LRU-очистка хранилища при достижении лимита.

4. **Очистка MainViewModel и UI**:
