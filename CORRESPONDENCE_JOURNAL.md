```

**[YYYY-MM-DD HH:MM TZ]** | От: [Имя] | Кому: [Имя] | Тип: [СООБЩЕНИЕ / ОТЧЁТ / АУДИТ / ЗАДАНИЕ / ЗАМЕЧАНИЕ / ПРИНЯТИЕ / ВОЗВРАТ]
```

5. В конце сообщения рекомендуется ставить разделитель `---` или просто оставлять пустую строку перед следующим заголовком.

### Отчёт по выполнению Этапа 4 (XFTP и файловый слой)

Все задачи ТЗ по Этапу 4 закрыты без компромиссов:

1. **Сегментирование и шифрование (`XftpProtocolEngine.createChunkedTransfer`)**:
   - Файлы разбиваются на фиксированные 64-килобайтные блоки (`DEFAULT_CHUNK_SIZE = 64 * 1024`).
   - Для каждого трансфера генерируется эфемерный 256-битный симметричный ключ шифрования.
   - Рассчитывается корневой Merkle SHA-256 хеш исходного файла.
   - Каждый чанк шифруется AES-256-GCM и получает индивидуальный SHA-256 хеш.
   - Генерируется стандартный XFTP URI вида:  
     `xftp://{serverEndpoint}/file/{transferId}?root={rootHash}&chunks={totalChunks}`.

2. **Реальный сетевой транспорт отправки (`uploadTransfer`)**:
   - Полностью удалены любые `delay()` и симуляции передачи.
   - Реализована последовательная отдача блоков через HTTP POST на:  
     `/api/v1/files/{transferId}/chunks/{chunkIndex}`.
   - В заголовках передаются метаданные протокола:  
     `X-XFTP-Version: 1.0`, `X-Chunk-Index`, `X-Chunk-Hash`, `X-Chunk-Size`, `User-Agent: ParanoidX-XFTP/1.0`.
   - Защита DNS-leak: при включённом Tor клиент конфигурируется через `Proxy(SOCKS, InetSocketAddress.createUnresolved("127.0.0.1", 9050))`.
   - Автоматическая изоляция: если эндпоинт заканчивается на `.onion`, отправка без Tor немедленно блокируется со статусом `FAILED`.
   - Честная обработка сетевых ошибок (offline, timeout, HTTP 4xx/5xx) с логированием в `xftpLogs`.

3. **Сетевой транспорт приёма и сборки (`downloadTransfer` & `reassembleFile`)**:
   - Чанки запрашиваются через реальный HTTP GET запрос.
   - При получении чанки сохраняются в манифест, расшифровываются ключом трансфера, и их SHA-256 хеш верифицируется против хеша в манифесте.
   - Производится итоговая сборка потока и валидация совпадения корневого Merkle root. В случае несовпадения хотя бы одного байта сборка прерывается с ошибкой целостности.

4. **Интеграция с ViewModel и UI**:
   - `MainViewModel.uploadXftpTransfer` переведён на реальный движок `XftpProtocolEngine.uploadTransfer` с передачей статуса Tor-демона и живым логом.

5. **Тестирование и верификация (`ExampleUnitTest`)**:
   - Добавлен комплексный тест `testRealXftpChunkingUploadDownloadAndReassembly`:
     - Поднимает встроенный JDK `HttpServer`.
     - Генерирует 150 KB бинарных данных (делятся ровно на 3 блока: 64KB, 64KB, 22KB).
     - Выполняет полный цикл `uploadTransfer` с проверкой HTTP заголовков и хешей каждого блока на стороне сервера.
     - Выполняет `downloadTransfer`, расшифровку и `reassembleFile` с побайтовым сравнением `assertArrayEquals`.
     - Проверяет честный отказ при отправке на закрытый порт без зависаний.
     - Проверяет блокировку `.onion` без Tor.
   - Все unit-тесты (`gradle :app:testDebugUnitTest`) успешно пройдены: **BUILD SUCCESSFUL in 1m 50s**.
   - `compile_applet` подтвердил чистую сборку приложения без ошибок.
